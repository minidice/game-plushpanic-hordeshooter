# 기록 문서 나누기 설계안 (기능 중심)

작성일: 2026-10-26. **설계안이다. 아직 옮기지 않았다.** 실제 이동은 열린 작업 브랜치가 모두 main에 합쳐진 뒤에 한 번에 한다(6장). 배경은 [작업 방식](work-process.md) 1.3 · 5장 ①, 결정 기록은 [decisions.md](decisions.md) T-26.

---

## 1. 왜 나누나

- 지난 7일(커밋 114개) 동안 가장 많이 바뀐 파일: `issues.md` 103번, `decisions.md` 98번, `feature-checklist.md` 88번. 모든 작업이 이 세 파일을 고친다.
- 충돌의 주원인은 **모든 작업이 같은 파일 끝에 긴 기록을 덧붙이는 것**이다.
  - `feature-checklist.md` 끝에 "이번 변경 확인 기록" 절이 계속 쌓임(지금 74개 절).
  - `issues.md`의 "열림" · "해결" · "기록 운영 이력"에 날짜별 긴 단락이 계속 쌓임(지금 절 114개).
  - 두 작업이 파일 끝에 동시에 덧붙이면 git은 거의 항상 충돌로 본다.
- 섞인 커밋도 생긴다(`656e2db`).

## 2. 원칙: 기능별 폴더, 그 안에서 작업 종류별 파일

사용자 작업 방식(2026-10-26): **서로 다른 두 기능을 동시에 만들기보다, 한 기능의 코드 · 데이터 · 리소스 작업을 따로 동시에 돌리는 경우가 많다.** 그래서 다음처럼 나눈다.

1. **기능별 폴더** — 한 기능의 결정 · 이슈 · 기록이 한곳에 모인다.
2. **폴더 안에서 작업 하나에 기록 파일 하나** — 같은 기능을 코드 · 데이터 · 리소스 작업이 동시에 고쳐도, 각자 새 파일을 만들므로 충돌하지 않는다.
3. **위쪽 세 문서는 짧은 색인만** — ID · 한 줄 요약 · 상태 · 링크. 한 줄 수정은 git이 대부분 자동으로 합친다(같은 줄을 동시에 고칠 때만 충돌).

## 3. 구조

```
doc/
├─ decisions.md            색인: ID · 한 줄 결정 · 상태 · 날짜 · 기능 폴더 링크
├─ issues.md               색인: ID · 한 줄 증상 · 상태 · 날짜 · 기능 폴더 링크
├─ feature-checklist.md    기능별 체크 항목만 (확인 기록 절은 두지 않음)
└─ features/
   ├─ combat/              전투 · 조작 (무기, 조준, 치명타, 근접, 피격, 반동)
   │  ├─ README.md         지금 규칙 요약 + 상세 규격 링크(weapon-spec.md 등)
   │  ├─ decisions.md      이 기능 결정의 본문(C-xx 전체 내용, 바뀐 결정)
   │  ├─ issues.md         이 기능 이슈의 본문(증상 · 원인 · 해결 · 재발 방지 · 검사 경로)
   │  └─ log/              작업 기록: 작업 하나 = 파일 하나
   │     ├─ 2026-10-26-code-crit-focus.md
   │     └─ 2026-10-25-art-reticle-pass2.md
   ├─ multiplayer/
   └─ …
```

- **기록 파일 이름**: `날짜-종류-주제.md`. 종류는 `code` · `data` · `art` · `doc`(문서만) · `check`(검사 · 검증만). 예: `2026-10-26-data-party-scaling.md`.
- **기록 파일 내용**: 지금 "이번 변경 확인 기록" 절에 쓰는 것을 그대로 쓴다. 변경 사항, 실행한 검사와 결과, 종료 경고, 렌더, 남은 제약, 관련 ID.
- **본문 파일(`features/*/decisions.md` · `issues.md`)**: 한 ID 항목 아래에 길게 쓴다. 표의 긴 한 줄 대신 소제목 + 문단이다. 같은 ID를 두 작업이 동시에 고칠 때만 겹친다.
- **상세 규격 문서**(`weapon-spec.md`, `multiplayer-sync-design.md` …)는 지금 자리에 둔다. 기능 `README.md`에서 링크만 한다. 위치를 옮기면 다른 문서의 링크가 많이 깨지므로 1차에서는 옮기지 않는다.

## 5. ID 규칙 (결정 필요)

새 ID를 두 작업이 동시에 같은 번호로 만드는 문제가 생긴다(예: 둘 다 `I-126`).

| 안 | 방법 | 장점 | 단점 |
|---|---|---|---|
| **A. 전체 번호 + 먼저 예약(추천)** | 새 ID가 필요하면 색인에 한 줄을 먼저 추가해 바로 커밋 · 푸시하고, 본문은 그다음 쓴다. 푸시가 충돌하면 받아서 다음 번호로 바꾼다 | 지금 번호 체계(I-1~I-125) 그대로, 익숙함 | 예약 커밋 한 번이 더 필요 |
| B. 기능 접두사 번호 | 새 이슈는 `I-C-01`(combat) · `I-L-01`(level)처럼 기능마다 따로 번호 | 동시에 만들어도 기능이 다르면 안 겹침 | 번호 체계가 둘이 됨, 같은 기능의 코드 · 리소스 작업끼리는 여전히 겹칠 수 있음 |

기존 ID는 어느 안이든 **바꾸지 않는다**(AGENTS.md: ID 중복 · 이력 삭제 금지).

## 6. 옮기는 방법

### 6.1 전제

- 열린 작업 브랜치가 없을 때 한 번에 옮긴다. 2026-10-26 기준 아직 안 합쳐진 브랜치: `codex/duck-clean-art` · `codex/goose-clean-art` · `codex/tiger-clean-art`(세 문서를 모두 고침), 오래된 `origin/claude/charming-cori-52tbyw`(2026-10-22).
- 옮기는 동안 다른 작업은 세 문서를 고치지 않는다.

### 6.2 순서

1. `doc/features/<기능>/`의 `README.md` · `decisions.md` · `issues.md` · `log/`를 만든다.
2. **`feature-checklist.md`의 "이번 변경 확인 기록" 절**을 해당 기능의 `log/날짜-종류-주제.md`로 하나씩 옮긴다. 체크 항목에는 기록 링크만 남긴다.
3. **`issues.md`의 긴 단락**(열림 · 해결 · 기록 운영 이력)을 기능별 `issues.md` 본문이나 `log/`로 옮긴다. 색인 표는 한 줄로 줄이고 본문 링크를 단다.
4. **`decisions.md`의 긴 표 줄**은 색인에 한 줄 요약만 두고, 전체 문장은 기능별 `decisions.md`에 그대로 옮긴다. "바뀐 결정" 표도 해당 기능으로 옮기고 색인에 링크를 둔다.
5. `AGENTS.md`의 기록 규칙을 7장 문안으로 바꾼다.
6. 확인한다(6.3).

**내용은 지우지 않고 옮기기만 한다.** 문장을 고쳐 쓰지 않는다. 옮긴 뒤에도 git 기록에 원래 위치가 남는다.

### 6.3 확인

- **링크 검사**: `doc/` 안의 상대 링크가 모두 실제 파일 · 제목을 가리키는지 스크립트로 확인한다.
- **ID 보존 검사**: 옮기기 전 세 문서에 있던 모든 ID(`D-` `M-` `C-` `T-` `L-` `A-` `Q-` `I-`)가 옮긴 뒤에도 색인에 정확히 한 번 있는지 확인한다.
- **분량 확인**: 옮기기 전후 전체 줄 수를 비교한다. 줄어든 만큼이 색인 요약으로 바뀐 것인지 본다.

### 6.4 대안: 앞으로만 새 구조로 (점진)

- 지금 세 문서는 그대로 두고 **새로 쓰는 기록부터** 기능 폴더 `log/`에 쓴다.
- 세 문서에는 짧은 줄만 추가한다.
- 옮기는 작업이 필요 없고 열린 브랜치와도 덜 부딪친다. 대신 한동안 기록이 두 곳에 나뉜다.
- 충돌을 바로 줄이는 효과는 거의 같다. 새로 쌓이는 긴 기록이 따로 가기 때문이다.

## 7. 바뀔 AGENTS.md 규칙 (문안)

> 기능 추가 · 동작 변경 · 버그 수정 시:
> - 작업 기록은 해당 기능 폴더 `doc/features/<기능>/log/날짜-종류-주제.md`에 **새 파일**로 쓴다(변경, 실행한 검사와 결과, 종료 경고, 렌더, 남은 제약, 관련 ID).
> - 결정 · 이슈의 본문은 `doc/features/<기능>/decisions.md` · `issues.md`의 해당 ID 아래에 쓴다.
> - `doc/decisions.md` · `issues.md`에는 ID · 한 줄 요약 · 상태 · 링크만, `feature-checklist.md`에는 체크 항목과 기록 링크만 고친다.
> - 새 ID는 5장의 규칙으로 만든다.

## 8. 결정할 것

1. 기능 폴더 목록(4장)을 이대로 할지.
2. ID 규칙: A(전체 번호 + 예약, 추천) 또는 B(기능 접두사).
3. 옮기는 방식: 한 번에 전부(6.2) 또는 점진(6.4, 추천 — 열린 브랜치가 계속 생기는 지금 작업 방식에 맞음).
