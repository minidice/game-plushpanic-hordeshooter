# 시체 유지·정리 정책과 성능 확인

기준: 2026-10-20. 사용자 요청으로 기존 45개 즉시 삭제 제한을 변경하고, 이후 일반/네임드 시체를 분리했다. **일반 시체의 100개는 정리 목표치이며 화면 안 시체를 강제 삭제하는 절대 상한이 아니다.** 네임드는 이 개수에 포함하지 않고 별도 시간으로 유지한다. 성능 문제가 나타나면 수치를 다시 조정한다.

## 등급과 설정 파일

등급은 [monsters.csv](../game/content/data/monsters.csv)의 `tier` 열로 지정한다. `common`은 인간형·크롤러·야생/무장 일반 동물·plush, `named`는 황소·풍선·끌개·덮치는 적·토사물 적·무장 정예병이다. 외형/행동 종류로 추정하지 않는다. 예전 표에 tier가 없으면 common, 잘못된 값은 오류를 기록하고 common으로 읽는다. 이 열을 추가했다고 인원별 능력치 보정이나 멀티가 구현된 것은 아니다.

유지 정책은 [corpse_retention.json](../game/content/data/corpse_retention.json)에서 편집한다. 일반 정책의 기존 숫자도 함께 옮겼다.

| JSON 항목 | 기본값 | 의미 |
|---|---:|---|
| `cleanup_interval_seconds` | 1 | 정리 검사 주기 |
| `common.target_count` | 100 | 일반 시체 정리 목표 |
| `common.keep_distance_m` | 28 | 관찰자 주변 보호 거리 |
| `common.minimum_age_seconds` | 10 | 일반 시체 최소 유지 시간 |
| `common.unseen_grace_seconds` | 5 | 화면/근거리 보호 종료 뒤 유예 시간 |
| `common.removals_per_pass` | 8 | 한 번에 정리할 일반 시체 최대 수 |
| `named.lifetime_seconds` | 300 | 네임드 시체 유지 시간, 기본 5분 |

설정은 스테이지의 Effects 생성 시 읽는다. 수정 후 새 게임/스테이지를 시작한다. 없는 항목은 기본값을 사용하고, 문법 오류·알 수 없는 키·잘못된 타입/범위는 파일/필드 이름을 포함해 경고한다. 시간은 초 단위이며 네임드 수명·검사 주기·회당 삭제 수는 양수여야 한다. `0`을 무한 유지로 해석하지 않는다. 모드별 JSON 덮어쓰기 선택은 아직 없으며, 현재는 모든 테마에 같은 파일을 사용한다.

## 네임드 시체

- 기본 300초 동안 일반 개수·거리·화면 정리에서 제외한다. 시간이 지나면 화면 안이어도 다음 검사 주기에 만료된다(기본 최대 약 1초 지연). 일시정지 중에는 게임 시간도 멈춘다.
- 생성 시 수명을 확정한다. 기존 시체의 타이머를 설정 변경으로 소급 갱신하지 않는다. 스테이지를 나가면 함께 제거되며 세이브 영속성은 없다.
- `NamedCorpseRecord`는 **고정된 사망 위치**, 스테이지 내 고유 `CorpseId`, 원본 `MonsterId`, 생성·만료 시각을 보존한다. `Effects.NamedCorpses`에서 접근한다.
- 움직이는 `Corpse` 외형은 이 기록 아래의 별도 물리 노드다. 외형이 굴러가거나 제거되어도 사망 위치/기록은 바뀌지 않는다. 기록 자체에는 충돌체가 없다. 외형의 지형·시체끼리 충돌은 유지하되 게임플레이에는 영향을 주지 않는다.
- **아이템 생성·루팅 UI/입력·소유권·저장·네트워크 복제는 미구현**이다. 미래 루팅은 로컬 시체 위치가 아닌 이 기록을 기준으로 하고, 호스트가 ID·사망 위치·만료 시간·루팅 상태를 확정해야 한다. 현재 ID는 로컬 스테이지 안에서만 유일하다.

## 일반 시체 정리 규칙

- `Effects.CorpseTargetCount` 기본 100. 그 이하에서는 개수 때문에 정리하지 않는다.
- 100개 초과 시 **먼저 생성된 시체부터** 확인한다. 다음 조건을 모두 만족하는 시체만 삭제한다.
  - 등록된 모든 관찰자에서 수평 거리 28m 초과.
  - 등록된 어느 카메라 화면에도 보이지 않음. 모델/꼬리/공중 자세를 고려한 보수적 경계와 화면 가장자리 96px 여유를 둔다. 벽에 가려졌다는 이유만으로 삭제하지 않는다.
  - 생성 후 10초 이상, 마지막으로 보호된 뒤 5초 이상 경과.
- 1초마다 확인하고 한 번에 최대 8개 정리한다. 오래된 시체가 보호 중이면 건너뛰고 다음 후보를 본다. 멀리 있다는 이유로 새 시체를 오래된 후보보다 먼저 지우지 않는다.
- 화면 안·가까운 시체만 남았다면 **100개를 넘겨 유지**한다. 관찰자 정보가 아예 없으면 안전하게 유지한다. 이동/정지에 따라 정리 조건을 다시 확인하므로 생성할 때만 검사하지 않는다.
- 구역 이름이나 월드 +X 좌표로 “지나온 구역”을 추정하지 않는다. 되돌아가거나 파티가 흩어졌을 때도 관찰자들의 실제 위치와 화면을 기준으로 판단한다.
- 이 정책은 `Effects.SpawnCorpse`의 **common 적 시체** 대상이다. 네임드는 위의 시간 정책을 적용한다. 플레이어 사망 시체는 관전 카메라 대상이므로 두 목록에서 삭제하지 않는다.

현재 코드: `game/scripts/World/EffectsCorpseRetention.cs`, `Effects.cs`, `Corpse.cs`. 정지 또는 최대 5초 후 시체 물리를 고정하고 반복 물리 콜백도 중지한다. 고정해도 메시 렌더·충돌 데이터 비용이 사라지는 것은 아니다.

## 멀티플레이와 충돌

일반/네임드의 움직이는 시체 외형은 **게임 판정과 분리된 로컬 연출**로 유지한다. 지형(`World`)과 다른 시체(`Corpse`)끼리만 충돌하고, 플레이어·적·드럼통·이동 가능한 상자에는 물리 영향을 주지 않는다. 시체 쪽 마스크뿐 아니라 드럼통/상자 쪽의 Corpse 마스크도 제거했다. 플레이어 사망 시체도 같은 충돌 마스크를 사용한다. 네임드의 고정 기록은 이 외형과 별개다.

따라서 두 클라이언트의 시체 유지 수가 달라도 시체 삭제 자체가 이동 경로나 드럼통 위치를 바꾸지 않도록 한다. 대신 시체가 이동 가능한 소품 위에 자연스럽게 걸리거나 소품을 밀어내는 연출은 포기한다. 새 게임플레이 물체에 Corpse 충돌을 추가하면 이 전제가 깨지므로 회귀 검사가 필요하다.

`RegisterCorpseObserver(anchor, camera)` / `UnregisterCorpseObserver(anchor)`로 여러 관찰자를 등록할 수 있고, 현재 Stage는 로컬 플레이어·카메라 한 쌍만 등록한다. 관찰자 없는 원격 플레이어가 자동 감지되는 구조가 아니다. **멀티 구현 시** 참가/퇴장·관전 전환 때 모든 플레이어의 위치와 카메라/화면 범위를 등록·갱신해야 한다. 카메라를 생략한 관찰자는 28m 거리 보호만 제공한다. 원격 관찰자 보호는 합성 2관찰자 검사로 확인했으며, 실제 네트워크 동기화는 아직 검증하지 않았다.

## 성능 측정

실행: 빌드·리소스 가져오기 후 Godot로 `res://tests/CorpsePerformance.tscn` 실행. 헤드리스는 렌더 성능 측정이 아니므로 이 장면은 거부한다.

- 장비: AMD Ryzen 7 9800X3D / NVIDIA GeForce RTX 5070 Ti.
- Godot 4.7.2 .NET, Forward+ Vulkan, Jolt, 1600×900, 프로젝트 기본 조명/그림자/AA, VSync 및 FPS 제한 해제.
- 실제 Stage 1 창고와 HUD. 살아 있는 적 제거, 디렉터 중지. 동일한 카메라에서 시체를 밀집 배치했다.
- 정지 시나리오는 1초 준비 후 각 4초 측정. 움직이는 시체는 첫 접촉을 포함해 생성 직후 4초 측정. 단일 실행이며 장시간/최저 사양 검증이 아니다.
- 프레임 시간은 실제 ProcessFrame 사이 벽시계 시간, 물리 시간은 Godot `TimePhysicsProcess` 모니터 값이다. GPU 단독 시간이 아니다. 시체 생성/모델 로딩 스파이크는 정지 시나리오 측정에서 제외됐다.

| 조건 | 평균 프레임 ms | p95 프레임 ms | 평균 FPS | 평균 물리 ms |
|---|---:|---:|---:|---:|
| 시체 없음 | 1.68 | 2.24 | 595 | 0.36 |
| 정지 감염체 45개 | 1.72 | 2.43 | 580 | 0.27 |
| 정지 감염체 100개 | 1.69 | 2.24 | 593 | 0.13 |
| 정지 감염체 160개 | 1.94 | 2.50 | 516 | 1.00 |
| 정지 동물 100개(4종 복제 좀비) | 5.35 | 6.68 | 187 | 0.19 |
| 움직이는 감염체 100개 | 1.86 | 2.54 | 537 | 1.06 |

100개 감염체가 45개보다 빠르게 측정된 작은 차이는 개선 효과로 해석하지 않는다. 실행 순서, 배경 소품의 안정화, 짧은 표본의 변동이 포함된다. 현재 장비·조건에서는 100개 목표를 유지하되, 부위/재질이 많은 동물 모델 쪽 비용이 크다는 점을 후속 최적화에 반영한다. 살아 있는 호드, 폭발·이펙트, 최대 6인 네트워크, 장시간 누적과 낮은 사양에서 동일 프레임을 보장하지 않는다.

원본: [성능 JSON](../game/output/corpse-performance.json), [실행 로그](../game/output/corpse-performance.log), [100개 실제 렌더](../game/output/corpses-100.png). 수치는 등급 분리 이전의 일반 시체 렌더 측정 결과이며 네임드 누적/루팅 성능을 측정한 것이 아니다. 재실행하면 달라질 수 있다.

## 회귀 검사와 남은 위험

`CorpseRetentionCheck.tscn`: 화면 안 100개 초과 유지, 2관찰자 보호, 거리와 별개인 카메라 보호, 유예 시간, 생성 순서, 보호 대상 건너뛰기, 분할 정리, 외부 삭제, 관찰자 누락, 양쪽 충돌 마스크, 실제 Jolt에서 소품 비간섭을 검사한다.

`CorpseTierCheck.tscn`: JSON 정상/오류/기본값, CSV 등급/구버전/오타, 6종 네임드 실제 사망 경로(풍선 포함), 개수 분리, 일반 정리 면제, 299초 유지/300초 만료, 커스텀 수명·검사 주기, 고정 위치/고유 ID, 외형 제거 뒤 기록 보존을 검사한다. 카메라 평면을 가로지르지만 화면 옆 멀리 떨어진 일반 시체도 정리되는지 확인한다. 300초를 실제로 기다리는 대신 같은 정리 함수에 게임 경과 시간을 주입한다.

`Integration.tscn`으로 기존 전투·사망 연출의 회귀를 함께 확인한다. `Start-Game.ps1 -Test`는 통합 검사만 실행하므로 전용 장면은 별도로 실행한다.

이번 실행 결과: C# 빌드 경고·오류 0, `CorpseRetentionCheck` 16개 통과, `Integration` 146개 통과, 실제 렌더 성능 장면 완료. 이전 코드에서는 화면 안 110개 유지 검사가 실패하는 것을 먼저 확인했다. 일부 검사 종료 시 ObjectDB 정리 경고는 남아 있으며 I-17로 추적한다. 로그: [정리/충돌 검사](../game/output/CorpseRetentionCheck-corpse-final.log), [통합 검사](../game/output/Integration-corpse-final.log).

이후 등급 분리 검증: `CorpseTierCheck` 36개, 기존 `CorpseRetentionCheck` 16개, `Integration` 146개 통과. 수정 전에는 네임드가 301초 뒤에도 남는 검사와 카메라 옆 먼 일반 시체가 정리되지 않는 검사가 실패함을 확인했다. 추가 검사는 고정 사망 기록과 외형 재부모화 뒤 충격량 보존도 포함한다. 등급 검사 종료의 ObjectDB 경고 11개도 I-17의 정리 대상이며, 기능 통과로 자원 정리 문제가 해결됐다고 간주하지 않는다. 로그: [등급/설정 검사](../game/output/CorpseTierCheck-tier-final.log), [기존 유지 정책 검사](../game/output/CorpseRetentionCheck-tier-final.log), [통합 검사](../game/output/Integration-tier-final.log). 이 단계에서 성능 장면은 재측정하지 않았다.

화면 안 일반 시체가 수백 개 쌓이거나 네임드가 5분 동안 많이 생성되면 총 시체 수는 100개보다 많아진다. 네임드에는 별도 개수 제한을 두지 않았다. 이때 화면 안 강제 삭제를 몰래 추가하지 않고, 부하 측정 후 LOD/재질 병합/연출 조절 또는 별도 정책 변경으로 다룬다. 멀티에서는 로컬 시체 외형을 엄폐물·길막·부활·루팅 판정으로 재사용하지 않는다. 네임드 루팅은 호스트 권한의 기록과 상호작용을 구현한 뒤 활성화해야 한다.
