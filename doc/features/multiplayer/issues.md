# 멀티플레이 — 이슈 본문

## I-135 큰 캠페인 좌표가 통신 범위를 넘음

- 상태·날짜: 열림, 2026-10-29. 예약 `ccfdede`를 먼저 커밋·푸시한 뒤 기록했다.
- 증상: 큰 캠페인1~3의 후반에서 참가자가 장치 앞에 있어도 사용할 수 없고, 모두 도착해도 세이프하우스 닫기가 활성화되지 않는다. 문 열림 상태 자체는 같아도 진행이 막힌다.
- 확인된 원인: `NetWriter.Cm`은 cm 좌표를 S16으로 제한한다. 범위는 −327.68~327.67m인데 현재 큰 맵은 +600m 이상이다. `NetInput` 위치와 스냅샷/사건의 위치 모두 같은 코덱을 쓴다. 클라이언트의 실제 x606.9/597/633 등이 호스트에서327.67로 잘려 `StageNet.ClientUse` 거리 검사와 `Stage.HumansInSafehouse` 판정이 실패한다. 후반 적·탄도·아이템 위치에도 같은 범위 문제가 적용된다.
- 해결: 미해결. 이번 작업은 전체 점검이며 제품 코덱/프로토콜을 변경하지 않았다. 위치 표현을 큰 맵 범위에 맞춰 변경할 때 양쪽 코덱·모든 패킷 크기 검사·프로토콜 버전을 함께 갱신해야 한다.
- 재발 방지·검사: `CampaignInteractionAudit`의 모든 진행 장치 좌표 왕복, 실제 ENet 참가자 요청, 끝 세이프하우스 전원 도착 검사. 범위를 넘는 요청과 호스트의 잘린 좌표를 로그에 함께 남긴다. [점검 기록](log/006-check-campaign-interaction-audit.md).
- 남은 제약: 아직 배포본에 존재한다. I-134 문 상태 수정으로 해결되는 문제가 아니다. 두 PC/인터넷 검사는 하지 않았다.

## I-136 사다리·집라인과 높이 동기화 누락

- 상태·날짜: 열림, 2026-10-29. 예약 `ccfdede`를 먼저 커밋·푸시했다.
- 증상: 캠페인 참가자가 E로 사다리나 집라인을 요청해도 자기 화면에서 출발하지 않고, 호스트의 대역만 이동하거나 다시 돌아온다. 캠페인1~3 사다리, 캠페인2~3 집라인에 해당한다.
- 확인된 원인: `ClientUse`는 호스트의 `Interactable.Use(who)`만 실행한다. `PlayerLadder.ClimbLadder`/`RideZipline` 시작과 종료는 소유자에게 전달되지 않는다. `HostMovesMe`에도 사다리/집라인이 없어 소유자는 계속 원래 위치를 전송한다. 추가로 `FollowVelocity`는 받은 Y를 버리고 수평으로만 따라가므로 높은 단에 있는 생존자 위치를 재현하지 못한다. x269 사다리와 x160/x124 집라인은 I-135의 범위 안에서도 실패하므로 좌표 잘림만의 결과가 아니다.
- 해결: 미해결. 이동 시작 승인·진행/종료·이동 소유권·높이와 착지 위치를 일관되게 전달하는 구현이 필요하다. 임의 순간이동이나 문 높이 변경으로 우회하지 않았다.
- 재발 방지·검사: `CampaignInteractionAudit`는 모든 배치 사다리의 양방향, 집라인 착지, 단차 위치 추종을 검사한다. 각 요청 전 시험 위치를 초기화해 앞선 낙하가 다음 요청을 오염하지 않게 했다. 직접 위치 배치는 검사 준비이며 자동으로 실제 이동 성공으로 세지 않는다.
- 남은 제약: 일부 먼 이동 장치는 I-135와 함께 실패한다. 전체 경로의 지형/충돌 여유 검사와 인터넷 지연·피격 중 취소는 별도다. [로그·범위](log/006-check-campaign-interaction-audit.md).

## I-137 곤돌라 출발·도착 동기화 누락

- 상태·날짜: 열림, 2026-10-29. 예약 `83dd396`을 먼저 커밋·푸시했다.
- 증상: 캠페인3 곤돌라에서 호스트가 전원 탑승 후 출발해도 참가자 곤돌라는 출발/완료 상태가 되지 않으며 목적지에 도착하지 못한다.
- 확인된 원인: `Gondola.TryDepart`/`Arrive`는 호스트의 승객·일시정지·배경·도착 위치만 바꾼다. `StageNet`의 World/사건에는 곤돌라 진행/완료 상태가 없고, Arrive가 OnGondola를 해제한 뒤 순간이동하므로 도착 위치를 보장하는 신뢰 전송도 없다. 참가자의 기존 위치 입력이 다시 대역을 움직일 수 있다. 출발 지점도 통신 좌표 범위를 넘어 I-135가 함께 발생한다.
- 해결: 미해결. 탑승자·출발 승인·연출 상태·도착 위치와 완료 상태/중간 합류 복원이 함께 필요하다.
- 재발 방지·검사: `CampaignInteractionAudit --audit-stage=3`에서 실제 맵의 전원 탑승을 준비한 뒤 호스트 출발 성공, 클라이언트 출발/완료/도착 실패를 검사한다. 호스트에서 Arrive를 호출해12초 연출 시간을 단축한다. 검사 세계는 물리적으로 분리됐지만 SceneTree를 공유하므로 독립 프로세스의 일시정지 동기화 검증은 아니다. 클라이언트 Net은 명시적으로 항상 처리해 시험용 전역 pause가 통신 자체를 막지 않게 한다.
- 남은 제약: 제품 미수정. 두 PC에서 연출/중간 접속/도중 이탈은 별도 검증이 필요하다. [전체 점검](log/006-check-campaign-interaction-audit.md).

## I-90 후속: 멀티 캠페인 연속 전환 점검

- 2026-10-29에도 기존 제약이 유지된다. `Stage.NextStageEnabled`는 오프라인 실제 게임 장면에서만 기본 활성화된다. 멀티 캠페인1·2를 끝내도 다음 맵으로 자동 이어지지 않고 끝 화면을 표시한다. `StageTransition`은 한 로컬 플레이어의 이월/장면 로딩 흐름이다.
- 이번 전수 점검에서 `NextStageEnabled` 실패를 기존 I-90으로 구분했다. 새 버그 ID를 만들거나 해결 처리하지 않는다. 맵 내부 장치 동기화 수정과 전원 장면 전환/장비 이월 구현은 별도 범위다. [기록](log/006-check-campaign-interaction-audit.md).

## I-134 캠페인 C1 출구에서 멀티 클라이언트가 막힘

- 증상: 큰 거리 끝에서 골목으로 넘어가는 C1 기지에서 오리가 출구를 통과하지 못한다. 사용자 영상과 위치 설명으로 해당 출구를 특정했다.
- 확인된 원인: `StageNet`이 문과 경보의 상태를 하나의 U8 비트 필드로 전송했다. 큰 캠페인 1은 문 10개이며 C1 출구는 인덱스8(9번째)이므로 열림 상태가 잘렸다. 호스트는 열린 문을 통과하지만 클라이언트에는 닫힌 충돌이 남았다. 높이 문제는 아니다. 동일 출구에서 가장 큰 일반 캐릭터 거위(충돌 높이2.18m)는 통과했고, 오리(2.06m)의 클라이언트 문 상태만 닫힌 것을 수정 전 검사로 재현했다. 열린 문은 충돌을 해제하며 문 위 장식은 충돌체가 아니다.
- 해결: 문과 경보를 각각 U16 개수와 각 항목 U8 상태로 전송하고 수신 시 로컬 개수를 검증한다. 기존 문의 열림 애니메이션과 경보 동작을 유지한다. `NetLobby.Protocol` 17→18로 올려 이전 전송 형식과의 혼합 접속을 막는다.
- 재발 방지·검사: `CampaignDoorNetCheck.tscn`이 실제 ENet 호스트/클라이언트의 큰 캠페인에서 C1 출구 스위치 조작, 가장 큰 일반 캐릭터와 오리의 물리 통과, 10개 문 교대 열림/전체 닫힘, 경보 독립 전송, 해석 오류0을 검사한다. 수정 전 실패, 수정 후13개 통과. [실행 기록](log/004-code-campaign-door-sync.md).
- 남은 제약: 높이가 원인일 때 적용하자는 사용자 조건에 해당하지 않아 통로 높이1.2배 변경은 하지 않았다. 전체 맵의 높이 여유를 새로 보증하는 검사는 아니다. 두 PC 인터넷 플레이와 I-72 위치 오차는 별도다. 양쪽 모두 프로토콜18 새 빌드를 사용해야 한다.

## I-133 로비에서 함께 시작하면 연결이 끊겨 메뉴로 돌아감

- 증상: 로비에서 준비한 뒤 함께 시작하는 클라이언트가 메뉴로 돌아가거나 로비 로딩 상태에 남는다. 시작 후 합류는 성공할 수 있다. 사용자 배포본 두 프로세스 관찰에서 제보했다.
- 확인된 원인: 큰 캠페인 맵 생성이 메인 스레드를 수 초 동안 막으며 ENet 패킷/응답 처리가 중단된다. 기존 연결의 신뢰 패킷 응답 대기 제한에 걸려 상대가 연결을 해제한다. 진단에서 호스트 시작2.867초→맵 완료8.690초(약5.8초), 클라이언트 맵 완료 시점12.311초에 `ServerDisconnected`, 이후3초 뒤 메뉴 복귀를 확인했다. 같은 경로에서 대기 제한만 변경한 뒤 정상화됐다.
- 해결: `NetLaunch.SetLoadingTimeout`으로 로비/로딩 중 ENet 대기를 factor32·최소30초·최대60초로 설정한다. 클라이언트 로비 진입과 호스트의 Hello 수신 시 양 끝에 적용한다. 호스트의 ClientReady 수신/클라이언트의 최초 World 수신에서 일반 최소5초·최대30초로 복구한다. 로비 복귀 시 다시 로딩 대기를 적용한다. 패킷 형식과 게임 판정은 바꾸지 않는다.
- 재발 방지: `LobbyStartCheck`는 서로 다른 두 프로세스에서 실제 MainMenu→Stage 전환·2인 동기화 유지→함께 로비 복귀→두 번째 시작을 검사한다. 기존 LobbyCheck는 장면 전환을 카운터로 대체하고, 기존 배포 EXE 검사는 시작 후 합류만 확인해 이 구간을 검증하지 못했다.
- 검사: 수정 전 세 번의 별도 프로세스 검사에서 시작 알림 미도착/메뉴 복귀를 재현했다. 수정 후 실제 큰 맵 시작, headless 두 라운드와 Forward+1280×720 두 라운드가 양쪽 종료0으로 통과했다. Lobby31·NetCodec12·NetSync32 통과. [실행 로그·남은 범위](log/002-code-lobby-loading-timeout.md).
- 남은 제약: 맵 생성 자체가 비동기화된 것은 아니다. 로딩 중 무응답 판정이 최대60초까지 늦어질 수 있으며 이를 넘는 로딩/실제 연결 단절은 보호하지 않는다. 서로 다른 두 PC·인터넷 지연/손실은 미검증이다. 위치 오차의 간헐 실패(I-72)는 별도이며 이번 수정으로 해결됐다고 처리하지 않는다.

## I-72 후속: 로컬 위치 동기화 검사 간헐 실패 (2026-10-29)

- 증상: `a5b1a49` main 병합 후 NetSyncCheck 1차에서 원격 플레이어 위치 오차0.88m(기준0.3m), 2차에서 적 추적 평균0.39m/최대1.91m(기준0.3m/1m)로 실패했다. 같은 코드·인수의 3차는32개 모두 통과했다.
