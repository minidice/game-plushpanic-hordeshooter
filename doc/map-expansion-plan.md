# 맵 확장 방향과 후속 작업

> 2026-10-23 사용자 대화 정리. **방향은 확정, 맵 확장은 미구현.** 이번에는 문서 저장·커밋·병합·푸시까지 진행하며 게임 지형이나 임무 코드를 바꾸지 않는다.

## 1. 확정된 목표

- 현재 맵은 비좁다. 단조로운 구간의 세부 소품 배치보다 전체 맵 구조와 공간 크기 검증을 먼저 한다.
- 시나리오는 **목적지로 전진하면서 넓은 구역을 통과하는 구조**다. 짧은 보상을 위한 갈림길과 임무 때문에 잠시 왕복하는 분기를 둔다.
- 진행로가 막혀 있으면 다른 장소에서 버튼/장치를 조작한 뒤 돌아와 열린 길로 진행하는 구성을 사용할 수 있다.
- 두 번째 모드(생존)는 **덕코프 지향의 넓은 맵 탐색**이 목표다. 시나리오의 전진 경로를 그대로 적용하지 않는다.
- 제작한 식생·암반·벽·펜스·설비 모델과 셰이더는 재사용한다. 맵 구조 변경에 필요한 좌표 재배치는 허용하되, 기존 미술 자산 자체를 폐기하는 작업으로 보지 않는다.

## 2. 모드별 설계 기준

| 항목 | 시나리오 | 두 번째 모드: 생존 |
|---|---|---|
| 중심 경험 | 넓은 공간에서 싸우며 목적지로 전진 | 넓은 지도에서 여러 장소를 탐색 |
| 분기 | 짧은 보상 탐색·임무용 왕복 | 탐색 장소와 경로 선택 중심 |
| 다음 설계의 초점 | 구역 폭·측면 이동·후퇴 공간·진행문/임무 연결 | 탐색 지역 간 연결과 방문 목적 |
| 현재 구현과 차이 | 좁은 선형 Stage 1·2를 재구성해야 함 | 현재 Stage 1 거점 방어 시제품(M-22)과 최종 목표가 다름 |

현재 생존 모드의 거점 방어를 유지·통합·대체할지는 미결이다. 탈출 방식, 사망 손실, 영구 인벤토리 등 덕코프의 다른 규칙까지 이번 대화로 확정한 것은 아니다. 세 번째 모드(서바이버)는 이번 방향 변경의 대상이 아니다.

## 3. 시나리오 구성 제안

아래는 확정된 방향을 구현하기 위한 **설계 제안**이며 구역 수·순서·시간을 확정한 평면도가 아니다.

- 넓은 전투 구역 안에 건물·암반·엄폐를 두어 측면 이동과 후퇴가 가능하게 한다.
- 문·다리·짧은 협로에서 잠시 좁아졌다가 다음 구역에서 다시 넓어지는 변화를 만든다.
- 보상 분기는 본선에서 잠시 벗어나 보급을 얻고 복귀하는 구성으로 제한한다.
- 임무 분기는 ‘막힌 진행로 확인 → 가까운 제어 지점 방문 → 장치 작동 → 열린 진행로로 복귀’를 기본 사례로 검토한다. 긴 구간을 반복 이동해야 한다면 복귀 지름길을 검토한다.
- 공간이 넓어져도 다음 목적지를 읽을 수 있도록 주요 지형·진행문·표지의 위치를 함께 설계한다.
- 현재 긴 띠 모양 지형의 길이만 늘리지 않고 폭과 내부 이동 여유를 먼저 검증한다.

## 4. 작업 순서

| 단계 | 작업 | 확인할 결과 |
|---|---|---|
| 1 | 전체 평면도: 주요 구역·시작/도착·분기·임무 지점 표시 | 주 경로와 분기 목적을 구분할 수 있음 |
| 2 | 단순 바닥·벽·큰 건물 덩어리로 크기 시안 제작 | 실제 이동 속도와 카메라에서 넓게 느껴지고 이동 피로가 과하지 않음 |
| 3 | 적 진입로·보급·임무/진행문 배치 | 분기 보상과 임무가 진행을 방해하지 않고 전투 공간이 확보됨 |
| 4 | 경로·카메라·성능·모드 영향 검증 | 플레이어/적/분대가 연결되고 다른 모드의 기존 동작을 깨뜨리지 않음 |
| 5 | 구조 확정 후 지형·식생·소품 마감 | 확정된 경계와 공간 용도에 맞춰 기존 자산 재사용 |

첫 규모 시안은 **Stage 2**에서 만든다(2026-10-23 사용자 확정, L-20). Stage 1도 확장 대상 검토에 포함하고 누락하지 않는다. 세부 장식 확대는 구조 검증 뒤로 미룬다.

## 5. 구현 전 결정할 항목

- ~~한 스테이지의 목표 플레이 시간~~ → **2026-10-23 결정: 20분**(L-19, 같은 날 30분에서 고침). 캠페인 1은 4 스테이지(L-22), 재시도는 스테이지 단위만(L-23). 남은 것: 20분 기준 보급 예산 · 디렉터 시간 습격 간격(평면도와 함께 제안).
- Stage 1·2 각각의 폭·면적·주 경로 길이·구역 수. 덕코프의 실제 면적을 측정한 값이나 확정 배수는 없다.
- ~~시나리오와 생존이 지리까지 공유할지~~ → **2026-10-23 결정(L-26): 공유하지 않고 아트 부품만 공유.**
- 기존 L-1 ‘우측 상단 진행 70%’를 주 경로/보상 분기/필수 임무 왕복에 어떻게 측정할지. 이번에는 규칙을 바꾸지 않는다.
- 임무 중 되돌아오는 길: **적은 다시 등장한다(2026-10-23 결정, L-27)**. 남은 것: 보상, 버튼 상태 및 열린 문 상태의 멀티 동기화·재시작 처리.
- 2026-10-23 추가 결정: 중간 안전 구역 약 10분 간격(L-24)과 죽은 사람의 복귀(M-32), 피날레는 방어 → 보스 → 탈출(L-25). 평면도(7.2의 1단계)에 중간 안전 구역 자리를 표시한다.

## 6. 현재 코드와 검증 경계

현재 관리 영역은 Stage 1 `130×24m`, Stage 2 `118×24m`이며 실제 통행 면적은 이 사각형 전체가 아니다. `StageMap.Create`는 생존에 Stage 1을 사용하므로 시나리오 지형 변경을 생존에 자동 전파하지 않도록 설계해야 한다.

확장 구현에서는 `StageMap`의 바닥/벽/문, `Area`와 흐름장, 카메라 경계, 조우/보급 데이터, 임무 진행과 모드 선택을 함께 검토한다. 기존 충돌/흐름장 해시는 현재 배치의 기준이다. 확장 시 실제 변경을 검토하고 계약을 갱신하며, 기준을 무조건 재생성해 막힌 길을 숨기지 않는다.

현재 자동 이동 검수는 기본 거위·지정 경로·두 조준 방향 범위다. 실전 전투·다른 캐릭터·저사양/6인 장시간·최종 미술 검수는 남아 있다. I-17 종료 객체 경고와 I-106 모드 검사 오류를 확장 완료나 이번 문서 정리로 해결했다고 처리하지 않는다.

## 7. 높이 단 · 연출 이동 · 아트 방향을 합친 작업 순서 (2026-10-23 제안)

같은 날 다른 작업에서 정한 [높이 단 규격](elevation-tiers.md)(L-15~L-18)과 아트 방향(A-25: 메인은 덕코프, 단차와 화면 밀도는 젤다 참고)을 이 계획에 합친 **제안 순서**다. 4장의 5단계를 바꾸지 않고 그 사이에 단 시스템과 이동 수단을 끼워 넣는다. 사용자 승인 전이며 코드는 바뀌지 않았다.

### 7.1 왜 합쳐야 하나

- **크기 시안(4장 2단계)에 단차가 들어가야 넓이를 제대로 잰다.** 같은 면적이라도 단차 · 사다리 · 내려가기 지점이 있으면 이동 시간과 전투 공간이 달라진다. 그런데 지금 코드는 평평한 바닥 전제라(I-107) 단 시스템 없이는 단차 시안을 만들 수 없다.
- **임무 왕복(3장)의 "복귀 지름길"은 연출 이동으로 풀린다.** 위 단의 제어 지점에서 장치를 켜고 짚라인 · 내려가기 지점으로 단숨에 진행로로 돌아오면, 왕복 피로를 줄이면서 연출도 생긴다.
- **넓은 구역 사이의 전환**은 곤돌라(가짜 배경, L-18)로 이을 수 있다. 협곡 전체를 실제 맵으로 짓지 않아도 된다.
- **마감(4장 5단계)은 A-25 · [실사풍 아트 방향안](grounded-art-direction.md) · [환경 개선 이력](environment-quality-plan.md)의 자산을 재사용**한다. 구조가 정해지기 전에 소품 · 식생 마감을 더 늘리지 않는다(1장과 같음).

### 7.2 순서

| 단계 | 작업 | 근거 | 끝났다고 볼 조건 |
|---|---|---|---|
| 0 | **사용자 결정** — 2026-10-23 완료: 스테이지 20분(L-19), 첫 시안 Stage 2(L-20), 맵 제작 방식 B → C(T-24), 위 단 적은 시야 밖 적처럼(L-21) | 5장, 7.3 | 결정 기록에 남음 ✓ |
| 1 | **전체 평면도** — 2026-10-23 Stage 2 초안 승인(L-29, [Stage 2 평면도 초안](stage2-floorplan.md)): 구역 · 시작/도착 · 보상 분기 · 임무 지점에 더해 **단 높이, 사다리 · 오를 수 있는 벽 · 내려가기 지점 · 짚라인 · 곤돌라 위치**, 보스전 평지(L-17) 표시 | 4장 1단계 + L-15~L-18 | 주 경로 · 분기 · 단 이동이 한 장에서 읽힘. L-1 측정 범위(주 경로 / 분기 / 임무 왕복) 제안 포함 |
| 2 | **단 시스템 핵심** — 2026-10-23 1차 구현([높이 단 규격](elevation-tiers.md) 14장, `ElevationCheck`): 단 지도, 계단 · 내려가기, 흐름장 단 연결, 조준 · 총 · 근접 · 투척 판정 | 높이 단 규격 12장 1~2 | 시험용 단차 맵에서 규칙대로 동작. **모든 칸이 0단인 맵은 지금과 같은 동작**(`EnvironmentReview` 월드 · 흐름장 해시, `MapCheck`, `Integration` 그대로) |
| 3 | **크기 시안**: 단순 바닥 · 벽 · 큰 덩어리 + 단차로 첫 시안 스테이지를 짬. 생존 모드에는 전파하지 않음(6장) | 4장 2단계 | 실제 이동 속도 · 카메라에서 넓게 느껴지고, 이동 피로 · 단 이동 시간이 과하지 않음 |
| 4 | **이동 수단**: 사다리(오르기 정속 · 내리기 빠르게) → 몬스터 이동 유형(기어오르기 · 점프 · 비행) → 짚라인 → 곤돌라(가짜 배경) | 높이 단 규격 12장 3~5 | 분대원이 리더를 따라 탐. 이동 유형마다 목표까지 경로가 있음 |
| 5 | **배치**: 적 진입로(오를 수 있는 벽 · 위 단 등장 지점 포함), 보급, 임무 · 진행문, 복귀 지름길 | 4장 3단계 | **위 단 공간마다 몬스터 접근 경로가 있음**(고지대 무적 방지), 보급 · 임무가 진행을 막지 않음 |
| 6 | **검증**: 경로 · 카메라 · 성능 · 모드 영향, 멀티 동기화(단 값 · 사다리 · 기어오르기 상태, 버튼 · 문 상태, 재시작) | 4장 4단계, 5장 | 2인 이상 실제 플레이에서 끊김 · 엇갈림 없음. 미측정 항목(6인 · 저사양)은 따로 표시 |
| 7 | **마감**: 기존 벽 · 식생 · 설비 자산 재배치, 가림 옅게 하기(I-91 ①), 단 가독성(절벽 윤곽 · 사다리 표식), 깊이 아트(아래가 보이는 안개 층 · 빛줄기) | 4장 5단계, A-25 | 사용자 시각 검수 |
| 8 | 두 번째 시나리오 스테이지(Stage 1 포함) 확장 → 생존 모드 넓은 탐색 맵 | 4장, 2장 | 별도 계획 |

2단계(단 시스템)와 1단계(평면도)는 서로 기다리지 않으므로 함께 진행할 수 있다. 3단계부터는 2단계가 끝나야 한다.

### 7.3 맵 제작 방식 — 결정 필요

지금 맵은 C# 코드에 좌표를 직접 적어 짓는다(`StageOneLayout.cs`, `StageTwoMap.cs`). 면적이 몇 배가 되고 단 값까지 칠하려면 이 방식은 고치기 · 보기 어렵다. 선택지:

| 안 | 내용 | 장점 | 비용 |
|---|---|---|---|
| A. 지금처럼 코드 | 좌표 · 도형을 C#에 계속 적음 | 추가 도구 없음 | 큰 맵에서 수정 · 확인이 느림, 단 지도 칠하기가 번거로움 |
| B. 데이터 파일 | 구역 · 벽 · 단 · 이동 수단을 JSON 등으로 적고 코드가 읽음(보급 · 조우 데이터와 같은 방식) | 기존 `StageMap` 블록 재사용, 차이 비교 쉬움 | 눈으로 보며 배치하지는 못함 |
| C. Godot 에디터 장면 | 그레이박스 · 단 · 표식을 에디터에서 배치하고, 문 · 등장 · 보급은 마커 노드로 둠 | 보면서 배치, 큰 맵에 유리, 나중의 절차적 생성(L-13)에 청크로 이어짐 | 장면 → `StageMap` 변환 코드와 검사 필요 |

**2026-10-23 결정(T-24): B로 시작해 C로 옮긴다. A는 새 맵 · 확장에 쓰지 않는다.** 1단계(평면도) · 2단계(단 시스템)와 함께 B의 데이터 형식을 정하고, 크기 시안(3단계)은 B로 짓는다. C(에디터 장면 → 같은 데이터로 변환)는 시안을 여러 번 고치는 과정에서 필요해지는 시점에 넣는다.
